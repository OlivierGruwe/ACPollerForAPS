1. Introduction & concepts

ACPollerForAPS is an XML integration engine that transforms invoice and document data between systems by configuration, with no custom code. It reads an XML file, maps it to the structure a target system expects, and delivers it. Typical use: exchange data between AP Essentials (APS/ReadSoft) and one or more ERPs (Dynamics AX, Comarch Optima).

Pipelines

The core concept is the pipeline: one input folder → one transformation → one output. Each pipeline is autonomous, with its own watched folder, schedule and output. You can run several pipelines side by side — for example one for each direction of an exchange:

  • APS → Optima: reads AP Essentials invoices, produces Comarch Optima XML, drops it where Optima imports it.
  • Optima → APS: reads Optima exports, produces AP Essentials XML.
A pipeline does one thing end to end. Different rhythms or different formats simply mean different pipelines — there is no routing to configure.

Architecture

ComponentRole
ACPollerForAPS.Core (DLL)Shared model, transformation engine, validation, encryption, stats. Referenced by both the service and the UI — a single source of truth.
ACPollerForAPS.Service.exeThe Windows service that runs the pipelines.
ACPollerForAPS.UI.exeThe configuration interface (WPF).

The configuration file

The service and the UI share a single settings.json, structured as { "Pipelines": [ ... ] }. The service reads it at startup and runs one worker per pipeline; the UI loads it automatically and edits it.

The service reads the configuration once, at startup. After a change through the UI, restart the service so it picks up the new config.

2. Installation & startup

Prerequisites

  • .NET Framework 4.8 runtime on the target machine.
  • Administrator rights (Windows service + Event Log).

Installer

Run the setup (ACPollerForAPS-Setup-2.0.0.exe). It asks for the install directory and lets you choose components — the Service and the Configuration interface. The installer stops any running service/UI first, copies the files, installs the service (which also creates the Windows Event Log source) and starts it. A default settings.json is deployed only if none exists, so the service can start on a fresh machine.

The uninstaller stops the service and the UI, removes the binaries and the service, but keeps logs\, stats\, pending\ and settings.json, so configuration and history survive an upgrade.

3. The configuration interface

The window has a branded header, a toolbar (New, Open, Save, Save as, Validate on the left; Dark theme, Help, Manual on the right), a pipeline selector bar, and tabs: General, Schedule, Output, Dashboard.

The pipeline selector (top) lists all pipelines with Add / Remove / Copy. Pick one and the tabs below show that pipeline.

5. Field mapping & output paths

The mapping grid defines the output fields, in order. Each field has:

PropertyMeaning
Output pathThe output column (CSV) or element path (XML). For nested XML, use / — e.g. NAGLOWEK/SPRZEDAWCA/NIP. Parent nodes are created and shared automatically.
Typetext · amount (decimals; Abs drops the sign) · date (Date in = input format).
Sourcefixed = constant · header/xpath = record value · line = current line value · sum = aggregate over lines (see below).
Value / PathConstant (fixed) / input XPath (others). Suggestions filtered by Source.
Dec. / AbsDecimals / absolute value for amounts.
Date inInput date format.
Only when (path) / equalsConditional write: the field is written only when a line node equals a value.

Conditional mapping

Some formats produce, per record, lines of different kinds where some columns differ (e.g. Vendor vs Ledger lines). A field can be written only when a line node equals a value; otherwise it stays empty. Set Only when (path) and equals on the field.

Line numbering

A line field whose Path is the special value #index produces the line number (1, 2, 3…) — useful for an LP / position number.

6. Nested XML output key feature

The XML output is built from the field Output paths plus a small set of structural settings, so even deeply nested formats (like Comarch Optima) are produced by configuration alone.

Structure settings (XML format section)

SettingRoleOptima example
Root elementThe root tag.ROOT
Namespace (xmlns)Default namespace on the root. Empty = none.http://www.cdn.com.pl/optima/dokument
Record elementTag wrapping one record.DOKUMENT
Line wrapperOptional container around all lines.POZYCJE
Line elementTag wrapping one line.POZYCJA

Structural tags come from these settings; the fields only fill the content. Header fields are placed under the record element, line fields under the line element, each at its Output path.

Sums (aggregation)

When the input has only lines but the target needs totals (e.g. Optima's RAZEM_NETTO), a field with Source sum and a line Path adds that value across all lines of the record. It respects Only when, so you can total a subset of lines (e.g. only debit lines).

Not covered by sums: values that combine two fields (e.g. gross = net + tax at total level) or per-rate VAT tables. Map those from the input if present, or handle them at implementation.

Reading nested input

Input paths can be nested too (e.g. NAGLOWEK/SPRZEDAWCA/NIP). Default namespaces in the input (as Optima uses) are neutralized automatically, so the paths stay simple.

Preview

Load a Sample XML, then click Preview to see the generated output. Refresh paths re-scans the sample. Validate (toolbar) checks every pipeline.

7. Delivery transports & retry queue

Each pipeline delivers its output through a transport, with configurable retry.

FS / FTPS / S3

TransportNotes
FSFile written to the output folder.
FTPSExplicit/implicit, certificate validation, encrypted password.
S3Bucket + key prefix; custom endpoint for MinIO/S3-compatible; encrypted secret.
Credentials are encrypted with DPAPI (machine scope). Encrypt on the target machine; a secret encrypted elsewhere cannot be decrypted there.

Failed deliveries & automatic retry

If a delivery fails after all retries, the generated file is moved to a pending queue (pending/<pipeline>/) and the sources are archived normally — nothing is lost. At the start of every run the service retries the queued deliveries, so the file is delivered as soon as the target is reachable again. Pending deliveries appear in the run summary and the Event Log.

8. ERP Providers (plugins) advanced

Most targets are handled by the default mapping provider with no code. For a target whose logic the mapping cannot express, a DLL implementing IErpExporter can be dropped in the providers/ folder next to the service; set the pipeline's Provider to its name. The service discovers it at startup; a broken DLL is logged and ignored. See PROVIDERS.md for the full guide.

9. Dashboard

The Dashboard tab gives an operations overview so you can see the integration is running well. It reads the run history the service records in the stats\ folder (one line per run).

The dashboard fills in as the service processes files. It reads stats\ next to the service executable, so the UI sees it directly when both are installed together.

10. Operations

Logs

NLog writes to logs\ next to the service exe, with daily + size rotation and purge. Each run logs a start line, per-file detail and a summary. Set the level to Debug in NLog.config for diagnostics.

Monitoring (Windows Event Log)

The service reports to a dedicated Windows event log ACPollerForAPS (source ACPollerForAPS.Service). Any enterprise monitor (Nagios, Zabbix, Centreon) reads it natively.

1000 / 1001InformationService started / stopped
1100InformationRun completed OK

Service lifecycle

Restart the service after changing settings.json.

SymptomLikely cause
